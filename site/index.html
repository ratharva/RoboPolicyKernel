Feeding the GPU: Can Ray Data keep up with robot policy training?

Early finding: batches are usually ready when training needs them. At effective batch 8, median input wait was 0.565 ms for π0.5 and 0.116 ms for MolmoAct2.

To compare GPU activity over the same part of training, I excluded the first 50 steps and measured steps 51–200. The logged GPU averaged 97.3% utilization for π0.5 and 58.3% for MolmoAct2. That gap calls for profiling the training work between batches; it does not by itself show that MolmoAct2 needs a different GPU.

Across each run’s full reporting window, input waiting accounted for 1.64% and 6.96% of wait + preprocessing + compute time, respectively. These are early measurements; the next experiment is a longer comparison with recorded hardware and matched training settings.

Foundation models increasingly learn from multiple kinds of data. For robot policies, that means camera video, robot state and actions, and language together. Can the data infrastructure keep up? Ray says its data stack handles multimodal AI at scale. I’m testing that promise on robot demonstrations, where every sample is a synchronized slice of video, state, and action chunks—and investigating how much distributing the data across training workers helps.

I’m starting with vision-language-action models (VLAs). A training sample can combine three camera views, a robot state vector, a chunk of future actions, and a language instruction. Those pieces may live in different formats, but they need to be aligned to the same observation time. If the next batch isn’t ready, the GPU waits.

π0.5 and MolmoAct2 have native fine-tuning pipelines to compare against. The practical question is whether migrating either to Ray is worth the work for its data optimizations.

For π0.5, these longer runs show no speed advantage from migration. Native OpenPI averaged 93.7% GPU utilization and 16.22 samples/s; my Ray version recorded 6.36 samples/s, less than half the throughput. Faster batch delivery alone didn’t translate into faster training in that experiment.

For MolmoAct2, the input pipeline looks like a promising reason to investigate migration. In the native batch-8 run, mean batch wait was about half a second; in the Ray run it was 0.163 ms. Full observed-window GPU utilization was 33.0% for native and 54.3% for Ray. These averages include early-run activity; the separate Ray-only comparison below excludes the first 50 steps.

My working conclusion is that Ray’s data optimizations are most useful when input delivery is holding training back. The experiments have different implementations and reporting schedules, and the saved logs don’t establish GPU model or count, so these are results from specific workloads rather than a general verdict on either stack.

RoboPolicyKernel is the testbed: it prepares demonstrations in LeRobot v3 format and connects Ray Data to Ray Train. It supports ACT, MolmoAct2, and π0.5 through policy adapters. The comparisons here focus on VLAs; world-model architectures are next.

Why exclude the first 50 steps? A short run can give early initialization and input-pipeline warmup more weight in its mean. The fixed steps 51–200 interval compares equal step counts without selecting the busiest part of either trace. It is a post-warmup comparison window, not proof of steady state. Longer runs are still useful.

The current training implementation starts GPU polling after policy construction. The measurements therefore do not establish that model loading caused the lower average. Historical launch and profiler traces would be needed to attribute the remaining idle periods.

Window-wide batch wait versus sampled step timings. The opening answer uses the recorded perf/io_bound_fraction: 1.64% for π0.5 and 6.96% for MolmoAct2, each from one full reporting window. In the current training code this is summed batch wait divided by summed wait, preprocessing, and forward/backward compute. Optimizer time is outside that denominator; it is not a percentage of total job runtime.

The individual phase timers are logged only every ten steps. Their sampled means can miss waits that the window accumulator includes, so dividing sampled mean wait by sampled compute time does not establish that the entire run spends under 0.1% waiting. Batch-wait timers also measure the interval before consumption, not upstream decode cost alone.

How the measurements are calculated. GPU utilization is the arithmetic mean of one device’s polling samples from the first scalar through the last logged training-loss timestamp, including startup and intervening work. For native π0.5, the end is estimated from the final checkpoint timestamp minus its save duration; its last loss window is at index 900 while GPU polls extend to 999. Later polling and checkpoint tails are excluded from the headline utilization.

Phase timing excludes step 0. Ray logs sampled individual steps; native timers can be interval averages. Native π0.5 compute includes optimizer work, while Ray reports the optimizer separately. Throughput uses step-weighted logged windows: nine for native π0.5, one for the newer Ray full run, and one for Ray MolmoAct2. Missing samples/s metrics are left as missing, rather than estimated from compute time. Checkpoint timers can include reporting, and run cadences differ.

These are workload observations with matched logged batch sizes, not a controlled framework benchmark. Hardware identity, camera choices, normalization, and full training settings still need to be archived together for that comparison.

02

Design decisions

Prepare once, then experiment on the same data. Decoding and alignment belong in preparation. Training consumes the resulting LeRobot v3 episodes. This lets me compare policies or training settings against the same prepared recordings, while measuring conversion separately from training-time batch delivery. The cost is an intermediate dataset to store and version.

Give each policy a small adapter contract. The shared loop calls build and forward_loss; adapters own model construction, processors, and policy-specific behavior. ACT, MolmoAct2, and π0.5 can share iteration and reporting without forcing their inputs or distributed setup into one implementation. A new policy adds an adapter and configuration wiring rather than a copy of the training loop.

Hold out whole episodes for validation. Neighboring frames share scene content, and action chunks overlap in time. Splitting by episode keeps those closely related samples together. Validation can then measure performance on held-out demonstrations. It drives checkpoint selection; windowed training loss drives early stopping.

Let FSDP2 own its checkpoint format. A sharded model needs every rank to participate in saving and loading. The adapter supplies distributed checkpoint hooks, while the loop keeps the common reporting and recovery flow. Checkpoints also record the epoch, step, normalization snapshot, and whether the epoch completed, so a save partway through an epoch can resume with the right interpretation.

These choices make the experiments easier to compare: preparation has its own boundary, model differences have a defined home, and evaluation and recovery have explicit semantics.

03

How the pipeline works

Robot demonstrations arrive in different forms: timestamped messages, videos alongside HDF5 arrays, or an existing LeRobot dataset. Before a model can learn from them, the camera frames, robot state, and actions need to agree on what happened at each step.

The project puts that work in a separate preparation stage. Once the data is ready, you can run another training experiment without decoding the original recordings again.

01 · Prepare

Raw demonstrations. Discover episodes, read the source format, decode cameras, and align observations with actions.

02 · Store

LeRobot v3. Keep tabular data, videos, and episode metadata in a common format that training can read.

03 · Train

Ray Data → Ray Train. Build action chunks, prepare batches, run the policy, and record metrics and checkpoints.

training.prepare_data owns the raw source. It chooses an ingestion strategy from the dataset schema. MCAP episodes go through the project's decoder and writer; existing LeRobot mirrors use LeRobot's migration tooling.

training.train starts with a prepared dataset. It resolves the dataset location, builds the data pipeline, and starts the training workers. Pretrained policies load their model weights as part of training setup.

With preparation and training separated, the same prepared episodes can feed multiple experiments. You can change the policy or training settings while reusing the data.

Datasets and robot schemas.

Each file in training/data_prep/schemas/ describes a dataset's camera names, state and action components, sampling rate, source location, and ingestion strategy. Those fields become a RobotSchema used by the rest of the pipeline.

Dataset source Input path What to know
abc130k XDOF/ABC-130k · MCAP + protobuf Decodes camera streams and aligns state/actions. Supports streaming or downloading raw episodes before conversion.
agibot_alpha AgiBot World Alpha · HDF5 + tar Downloads archive shards and converts their HDF5 data and videos into prepared episodes.
droid cadene/droid_1.0.1 · LeRobot v2.1 Uses LeRobot's v2.1 → v3 migration to prepare the full mirror.
droid_100 lerobot/droid_100 · LeRobot v3 A smaller mirror with its own schema. Its 7-dimensional state/action layout differs from the full DROID schema's 8-dimensional layout.

Cameras and actions are part of the dataset contract. The schema records component names and dimensions in order. That order matters: it defines how the state and action vectors are assembled. Some datasets also expose depth cameras or alternative action spaces, such as joint and end-effector representations.

A new robot that fits an existing ingestion format may only need another YAML file. Custom message structures and HDF5 layouts plug in through their own decoding strategy.

Reusing prepared episodes. The MCAP path tracks converted source episodes in a manifest. Growing an episode request can reuse existing conversions and append new ones. Use a separate output directory when you want to keep multiple prepared versions.

Supported policies.

The shared loop needs to know how to construct a policy and how to get a loss from a batch. Each policy adapter supplies those operations, along with hooks for things like distributed wrapping and checkpoint formats when needed.

Policy Adapter behavior Configuration to look at
ACT Observation-to-action training without task text; uses the standard distributed path. training/configs/act_example.yaml
MolmoAct2 Uses task text; exposes LoRA, full fine-tuning, and freeze modes, with DDP or FSDP2 options. training/configs/molmoact2_example.yaml
π0.5 Loads a pretrained checkpoint and uses task text; exposes DDP and FSDP2 options and checkpoint-aware normalization. training/configs/pi05_example.yaml

The adapter contract lives in training/model/registry.py. Its core operations are build and forward_loss; optional hooks cover distributed setup, saving/loading, and normalization. The loop handles batch iteration, optimization, reporting, and evaluation around them.

Ray Data builds the model inputs. The reader loads the prepared episode data and cameras. The data pipeline forms future action chunks, handles padding at episode boundaries, and prepares image and state/action inputs. Where relative actions are requested, the conversion aligns action components with their corresponding state components by name.

Normalization connects the current dataset to the pretrained model’s input conventions. The pipeline separates the normalization mode from the source of its statistics, so a run can use a checkpoint's expected scheme with statistics computed for the current dataset. π0.5 also selects [0, 1] image scaling by default.

Ray Train runs the workers. The driver builds the run configuration and launches a TorchTrainer. Each worker constructs its policy through the adapter and enters train_loop.py. The standard path uses Ray's PyTorch wrapping; the FSDP2 adapters supply their own wrapping and sharded checkpoint hooks.

Settings include gradient accumulation, learning rates, mixed-precision options, and reporting intervals. Each policy keeps its own model settings in the corresponding config.

Validation, test, and early stopping have different jobs. By default, the configuration holds out 10% of episodes for validation. Splitting by episode keeps adjacent frames from the same demonstration together. You can also provide separate prepared roots for validation and test data.

Validation loss determines checkpoint retention when validation is enabled. An optional test split provides a separate evaluation after training. Early stopping follows windowed training loss, while validation loss guides checkpoint selection.

Metrics and history. TensorBoard logs live under the run directory. Optional W&B logging adds another place to inspect metrics and recorded episode media. ray_data_stats.txt records data execution statistics, and history.jsonl under the storage root records the history of your runs.

Checkpoints and recovery. Checkpoint settings control retention and whether saving happens only on improvement. The default keeps the best-scoring checkpoints and the latest checkpoint for recovery. With validation disabled, checkpoint scoring falls back to training loss.

Ray supports worker recovery within the same trainer.fit() call by restarting the worker and loading its checkpoint. The saved epoch, step, and epoch-completion marker distinguish a mid-epoch save from a completed epoch.

The repository also includes opt-in asynchronous checkpoint writing for the standard DDP path. FSDP2 uses its adapter's separate checkpoint implementation.

04

What Ray adds

Ray Data supplies the data execution pipeline, and Ray Train supplies worker orchestration and checkpoint reporting. My review so far is that this is a useful foundation: the newer Ray runs show small batch waits, and the same training structure accommodates several policies. The engineering work is in defining exactly what a robot sample means and making the model, data, and recovery paths agree.

Layer Robotics-specific work in this project
Raw recordings Schema-driven ingestion, camera decoding, state/action alignment, and incremental episode conversion.
Training samples LeRobot v3 reading, episode-aware action chunks, padding masks, and camera-key mapping.
Policy inputs Model processors, task text, image scaling, and explicit state/action normalization modes and statistics.
Distributed training Policy adapters, DDP/FSDP2 wrapping, and sharded save/load hooks.
Experiment visibility Separate batch-wait, preprocessing, compute, optimizer, GPU utilization, and checkpoint/report timings.

Optimizations already recorded. An earlier ABC-130k preparation measurement put video decoding at roughly 156 of 172 seconds for a three-camera episode. Decoding the cameras concurrently brought total episode preparation to about 83 seconds—roughly 2.1× faster in that measurement. This is a preparation-stage result; it describes different work from the sub-millisecond training-time median batch wait above. Preparation timing notes.

The newer TensorBoard extraction now puts the π0.5 optimization trial at 348.7 ms mean compute, over five sampled steps in a 50-step run. It also brings the September 14 MolmoAct2 Ray training run into the comparison. These results replace the older compute figures as the experiments to carry forward. See the per-run tables and measurement windows above.

The next experiments.

  1. Match the native and Ray workloads. Fix global batch, cameras, normalization, precision, optimizer, hardware, and evaluation/checkpoint cadence. Then compare throughput and utilization over the same interval.
  2. Sweep data-pipeline concurrency. Measure batch-wait p50/p95, samples/s, CPU memory, and per-device GPU utilization as concurrency grows. The hypothesis is that more input workers help only once batch delivery stops keeping up with compute. Separately, vary the number of training workers to measure how data sharding changes aggregate throughput and per-device waiting.
  3. Separate checkpoint work from training. Vary validation and save cadence, and time snapshot creation, writing, reporting, and final drain independently. The hypothesis is that reducing time between training windows raises sustained utilization even when batch wait is already low. Carry the π0.5 optimization-trial settings into a longer run, and compare both MolmoAct2 loaders with explicitly saved freeze settings and action horizons.

That is the research question I’m pursuing: how much of the available GPU time can this pipeline turn into useful policy updates, and which layer needs to change next?

05

Try it

The commands below prepare 20 episodes of one ABC-130k task, then run at most 50 training steps. This gives you a short first experiment to explore the workflow. Run the commands from the repository root in your Python environment, with a CUDA-capable setup for GPU training.

1. Install the training dependencies.

pip install -r training/requirements.txt

For ABC-130k, accept the dataset's access terms and set HF_TOKEN in your environment before preparation. The requirements file also lists optional dependencies: peft for MolmoAct2 LoRA, accelerate for the FSDP2 paths, and wandb for W&B logging.

2. Choose a task and prepare it.

# List tasks and episode counts.
python -m training.data_prep.discover --dataset-source abc130k

# Prepare a small set of episodes for training.
python -m training.prepare_data \
  --dataset-source abc130k \
  --tasks arrange_the_flowers \
  --max-episodes-per-task 20

The default output for this task is training/lerobot_v3/abc130k/arrange_the_flowers. You can choose another location with --v3-root and pass that same location to training.

3. Train on the prepared data.

python -m training.train \
  --dataset-source abc130k \
  --tasks arrange_the_flowers \
  --policy-type act \
  --max-train-steps 50 \
  --storage-root training/runs \
  --run-name act-first-run

The dataset flag lets training derive the preparation directory. Alternatively, pass --v3-root explicitly; the prepared metadata can identify the dataset source. --policy-type must be supplied explicitly.

4. Inspect the run.

python -m training.history --storage-root training/runs

tensorboard --logdir training/runs/act-first-run/tensorboard

For repeatable experiments, move settings into a YAML config and override only what changes:

python -m training.train \
  --dataset-source abc130k \
  --tasks arrange_the_flowers \
  --policy-type act \
  --config-file training/configs/act_example.yaml \
  --max-train-steps 50

Explicit CLI settings take precedence over the config file. The model's type in YAML must match --policy-type.

06

Extend it & explore the code

Add a dataset or robot. Start with the closest schema in training/data_prep/schemas/. Set the actual camera keys, state/action layout, sampling rate, source, and strategy-specific fields from the data you have inspected. Dataset choices are discovered from these YAML files.

For a new raw format, add a module under training/data_prep/strategies/, register it, and wire its preparation path where needed. Some formats fit per-episode conversion; others need their own orchestration because episodes share archive files.

Add a policy. Implement build_policy_and_processor and forward_loss in a new model module. Add its adapter dispatch in training/model/registry.py, its typed overrides in training/config.py, and the CLI wiring in training/train.py. Supply wrapping and checkpoint hooks if the policy needs a custom distributed path.

The adapter keeps model-specific changes local while the common loop continues to handle iteration, reporting, and checkpoint recovery.
