RoboPolicyKernel / Project guide

From robot demonstrations
to policy training.

A training pipeline built around a simple idea: changing the dataset or policy should not mean starting over with the rest of your code.

RoboPolicyKernel prepares robot teleoperation data in LeRobot v3 format, loads it with Ray Data, and trains policies with Ray Train. It brings ACT, MolmoAct2, and π0.5 into the same workflow, with separate adapters for the parts each model does differently.

01 / THE PIPELINE

Prepare once. Train from the result.

Robot demonstrations arrive in different forms: timestamped messages, videos alongside HDF5 arrays, or an existing LeRobot dataset. Before a model can learn from them, the camera frames, robot state, and actions need to agree on what happened at each step.

The project puts that work in a separate preparation stage. Once the data is ready, you can run another training experiment without decoding the original recordings again.

01 · Prepare

Raw demonstrations

Discover episodes, read the source format, decode cameras, and align observations with actions.

02 · Store

LeRobot v3

Keep tabular data, videos, and episode metadata in a common format that training can read.

03 · Train

Ray Data → Ray Train

Build action chunks, prepare batches, run the policy, and record metrics and checkpoints.

training.prepare_data owns the raw source. It chooses an ingestion strategy from the dataset schema. MCAP episodes go through the project's decoder and writer; existing LeRobot mirrors use LeRobot's migration tooling.

training.train starts with a prepared dataset. It resolves the dataset location, builds the data pipeline, and starts the training workers. Pretrained policies load their model weights as part of training setup.

With preparation and training separated, the same prepared episodes can feed multiple experiments. You can change the policy or training settings while reusing the data.

02 / DATASETS & ROBOTS

Different recordings, a common description.

Each file in training/data_prep/schemas/ describes a dataset's camera names, state and action components, sampling rate, source location, and ingestion strategy. Those fields become a RobotSchema used by the rest of the pipeline.

Dataset source Input path What to know
abc130k XDOF/ABC-130k · MCAP + protobuf Decodes camera streams and aligns state/actions. Supports streaming or downloading raw episodes before conversion.
agibot_alpha AgiBot World Alpha · HDF5 + tar Downloads archive shards and converts their HDF5 data and videos into prepared episodes.
droid cadene/droid_1.0.1 · LeRobot v2.1 Uses LeRobot's v2.1 → v3 migration to prepare the full mirror.
droid_100 lerobot/droid_100 · LeRobot v3 A smaller mirror with its own schema. Its 7-dimensional state/action layout differs from the full DROID schema's 8-dimensional layout.

Cameras and actions are part of the dataset contract

The schema records component names and dimensions in order. That order matters: it defines how the state and action vectors are assembled. Some datasets also expose depth cameras or alternative action spaces, such as joint and end-effector representations.

A new robot that fits an existing ingestion format may only need another YAML file. Custom message structures and HDF5 layouts plug in through their own decoding strategy.

Reusing prepared episodes

The MCAP path tracks converted source episodes in a manifest. Growing an episode request can reuse existing conversions and append new ones. Use a separate output directory when you want to keep multiple prepared versions.

03 / POLICY ADAPTERS

Keep the model-specific work in the model.

The shared loop needs to know how to construct a policy and how to get a loss from a batch. Each policy adapter supplies those operations, along with hooks for things like distributed wrapping and checkpoint formats when needed.

Policy Adapter behavior Configuration to look at
ACT Observation-to-action training without task text; uses the standard distributed path. training/configs/act_example.yaml
MolmoAct2 Uses task text; exposes LoRA, full fine-tuning, and freeze modes, with DDP or FSDP2 options. training/configs/molmoact2_example.yaml
π0.5 Loads a pretrained checkpoint and uses task text; exposes DDP and FSDP2 options and checkpoint-aware normalization. training/configs/pi05_example.yaml

The adapter contract lives in training/model/registry.py. Its core operations are build and forward_loss; optional hooks cover distributed setup, saving/loading, and normalization. The loop handles batch iteration, optimization, reporting, and evaluation around them.

04 / YOUR FIRST RUN

Start with a small ACT experiment.

The commands below prepare 20 episodes of one ABC-130k task, then run at most 50 training steps. This gives you a short first experiment to explore the workflow. Run the commands from the repository root in your Python environment, with a CUDA-capable setup for GPU training.

1. Install the training dependencies

pip install -r training/requirements.txt

For ABC-130k, accept the dataset's access terms and set HF_TOKEN in your environment before preparation. The requirements file also lists optional dependencies: peft for MolmoAct2 LoRA, accelerate for the FSDP2 paths, and wandb for W&B logging.

2. Choose a task and prepare it

# List tasks and episode counts.
python -m training.data_prep.discover --dataset-source abc130k

# Prepare a small set of episodes for training.
python -m training.prepare_data \
  --dataset-source abc130k \
  --tasks arrange_the_flowers \
  --max-episodes-per-task 20

The default output for this task is training/lerobot_v3/abc130k/arrange_the_flowers. You can choose another location with --v3-root and pass that same location to training.

3. Train on the prepared data

python -m training.train \
  --dataset-source abc130k \
  --tasks arrange_the_flowers \
  --policy-type act \
  --max-train-steps 50 \
  --storage-root training/runs \
  --run-name act-first-run

The dataset flag lets training derive the preparation directory. Alternatively, pass --v3-root explicitly; the prepared metadata can identify the dataset source. --policy-type must be supplied explicitly.

4. Inspect the run

python -m training.history --storage-root training/runs

tensorboard --logdir training/runs/act-first-run/tensorboard

For repeatable experiments, move settings into a YAML config and override only what changes:

python -m training.train \
  --dataset-source abc130k \
  --tasks arrange_the_flowers \
  --policy-type act \
  --config-file training/configs/act_example.yaml \
  --max-train-steps 50

Explicit CLI settings take precedence over the config file. The model's type in YAML must match --policy-type.

05 / INSIDE TRAINING

What happens between a recording and a loss?

Ray Data builds the model inputs

The reader loads the prepared episode data and cameras. The data pipeline forms future action chunks, handles padding at episode boundaries, and prepares image and state/action inputs. Where relative actions are requested, the conversion aligns action components with their corresponding state components by name.

Normalization connects the current dataset to the pretrained model’s input conventions. The pipeline separates the normalization mode from the source of its statistics, so a run can use a checkpoint's expected scheme with statistics computed for the current dataset. π0.5 also selects [0, 1] image scaling by default.

Ray Train runs the workers

The driver builds the run configuration and launches a TorchTrainer. Each worker constructs its policy through the adapter and enters train_loop.py. The standard path uses Ray's PyTorch wrapping; the FSDP2 adapters supply their own wrapping and sharded checkpoint hooks.

Settings include gradient accumulation, learning rates, mixed-precision options, and reporting intervals. Each policy keeps its own model settings in the corresponding config.

Validation, test, and early stopping have different jobs

By default, the configuration holds out 10% of episodes for validation. Splitting by episode keeps adjacent frames from the same demonstration together. You can also provide separate prepared roots for validation and test data.

Validation loss determines checkpoint retention when validation is enabled. An optional test split provides a separate evaluation after training. Early stopping follows windowed training loss, while validation loss guides checkpoint selection.

06 / RESULTS & RECOVERY

A run should leave enough behind to understand it.

Metrics and history

TensorBoard logs live under the run directory. Optional W&B logging adds another place to inspect metrics and recorded episode media. ray_data_stats.txt records data execution statistics, and history.jsonl under the storage root records the history of your runs.

Checkpoints and recovery

Checkpoint settings control retention and whether saving happens only on improvement. The default keeps the best-scoring checkpoints and the latest checkpoint for recovery. With validation disabled, checkpoint scoring falls back to training loss.

Ray supports worker recovery within the same trainer.fit() call by restarting the worker and loading its checkpoint. The saved epoch, step, and epoch-completion marker distinguish a mid-epoch save from a completed epoch.

The repository also includes opt-in asynchronous checkpoint writing for the standard DDP path. FSDP2 uses its adapter's separate checkpoint implementation.

07 / EXTENDING THE PROJECT

Where a new dataset or policy fits.

Add a dataset or robot

Start with the closest schema in training/data_prep/schemas/. Set the actual camera keys, state/action layout, sampling rate, source, and strategy-specific fields from the data you have inspected. Dataset choices are discovered from these YAML files.

For a new raw format, add a module under training/data_prep/strategies/, register it, and wire its preparation path where needed. Some formats fit per-episode conversion; others need their own orchestration because episodes share archive files.

Add a policy

Implement build_policy_and_processor and forward_loss in a new model module. Add its adapter dispatch in training/model/registry.py, its typed overrides in training/config.py, and the CLI wiring in training/train.py. Supply wrapping and checkpoint hooks if the policy needs a custom distributed path.

The adapter keeps model-specific changes local while the common loop continues to handle iteration, reporting, and checkpoint recovery.
